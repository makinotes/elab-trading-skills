# Mode C · playbook 沉淀（把规律炼成成型打法）

> elab-trade 的 playbook 分册。用户要"把攒下的规律炼成可复用 playbook"时走这里。数据是用户自己的，教方法不给方向（930）。

## 输入（从哪来）
- **`00_想法区/`（raw 交易想法，见 §〇）** —— 沉淀的最上游入口
- Mode A 的 `02_规律/`（随手记的规律）+ `03_定格/` 平仓复盘
- Mode B 交割单复盘出的"赚钱策略 / 高频错误"
- 用户口述"我一般怎么做 X"

**没素材别硬编**：让用户先用 Mode A 记几笔、或 Mode B 复盘一轮，攒够样本再炼。

## 〇 · 想法区（raw 交易想法暂存 · 沉淀的入口）⭐
不是所有东西都够格当 playbook 条目。刚冒出来、**还没验证**的交易想法先落这里——别丢，也别假装它已经是规律。这是"沉淀自己的交易想法"的家。

**位置**：使用本轮已确认的交易项目根（见主 Skill A.2）；没有交易项目时用 `<状态根>/playbook/`，不得猜成当前 cwd 或其他宿主目录。用户指定文件则沿用该文件。新想法追加，旧条目/证伪记录不覆盖；每项携带来源和权限。

**格式（每条一小块，存项目根的 `00_想法区/想法.md` 或 playbook 顶部）**：
```
- **想法**：<一句话，如 "IV 分位>75 卖 put 收租好像稳">
- **当时依据**：<为什么这么想——某个观察/数据/哪笔交易触发的>
- **待验证什么**：<要攒什么样本 / 看到什么才能确认或推翻>
- 标签+日期：`[想法 待验证]` <date>
```

**晋级漏斗（想法是起点不是终点）**：
```
[想法 待验证] → 相关交易每次回填、攒同类样本 → 够 n 笔 → 转 02_规律 → 过四关(§一) → 成型 playbook 条目(§二)
```
- **进度可视化**：先按 `_shared/trading-consistency.md` 核对同一规则版本与可比条件，再计入该组的去重样本 n。显示 `[想法 待验证 · 本版本可比样本 3/10，达到数量门槛后仍须过四关]`；不同版本、环境或未知版本分别记，不合并凑数，重复回填不重复增加。条件或版本未确认的观察不计入“本版本可比样本”，只记观察条数和待确认字段。
- 被证伪的想法 → 标 `[证伪 <date>]` **留着别删**（看得到想法的生死 = 认知进化的痕迹）
- 开仓前也回查想法区的待验证项（"这次是不是在验证那个想法？"）
- **禁止**：想法直接当规律下重注（没过样本+四关 = 过拟合到直觉）。**n≥10 是本工具的最低复核门槛，不是统计有效性保证**；小样本的不确定性很大，达到门槛仍须核对可比性与其余三关

## 一、一条规律怎么才算数（炼法 · 命门）⭐
别把"最近赚钱的做法"当规律（容易是运气 + 过拟合到最近行情）。进 playbook 要过四关：
1. **样本量够**：标清 n=多少。**n<10 一律标 `[样本不足 待验证]`，不当正式条目执行**。可以报告实际样本中的胜负数与比例，但不能当作未来胜率；置信区间须声明计算方法与成功次数，不能仅凭 n 写固定区间。n≥10 只是进入复核的最低流程门槛，仍需满足其余三关，不足则作为暂定假设继续记录
2. **有逻辑解释**：说得清"为什么会赢"（收 theta？波动率均值回归？），不只是统计巧合
3. **分离运气 vs 技巧**：结果好≠规律对，问"同样条件再来还合理吗"
4. **配失效条件**：什么市况/前提下不灵（没失效条件的规律是假规律）
未过关的保留待验证状态；AI提出的模式标 `[AI暂定模式 <YYYY-MM-DD>]`，用户自己的想法保留用户来源并标 `[想法 待验证]`，不能仅因未验证就改成AI来源。先别当正式条目。

## 二、playbook 条目框架（每条策略一张，每字段怎么填）
```
## 策略：<名字，如 IV 高位卖 Put 收租>
- 规则标识与版本：<稳定标识 + 本版版本号或不可变快照引用；缺历史记录标待确认，不倒填>
- 生效与范围：<确认/生效时间；适用新交易或哪些持仓；未确认则标待确认>
- 适用市况：<可判断：趋势/震荡 + IV 高低 + 事件前后>，如"IV 分位>70 且无临近财报"
- 进场条件：<量化到能照做：标的筛选/IV 分位/技术位/Delta 区间>
- 仓位规则：<单笔占比上限 + 加仓规则>，如"单笔≤总仓5%，不加仓"
- 止盈：<规则>，如"收到 50% credit 平"
- 止损/认错：<明确触发的证伪条件>，如"跌破 X 支撑/亏 Y% 平"
- 对冲：<配什么对冲>（参 elab-deconstruct，核对保护对象、区间及剩余风险；CC/BPS 不能笼统当作已有多仓的完整下行保护）
- 失效条件：<什么市况不成立>，如"IV 持续低位/单边下杀别用"
- 历史表现：<你真实数据：胜率/盈亏比/样本 n>，标 [我的数据]，n 不够标"样本不足"
```
填不出的标"待补"，**不替用户编**（尤其历史表现的胜率/数字，只用真实数据）。

## 三、沉淀流程
1 按策略类型、可比条件与规则版本分组，未知版本单列 → 2 每组规律过四关，不能借总体样本量晋级，够格炼成条目、不够进"暂定"区 → 3 用户明确提供的记录标 `[我的数据]`；AI 对记录的解释标 `[AI推测]`，用户未说明的进场条件或规则版本一律保留未知，不因将结果写入用户文件而改变归属 → 4 写成已确认项目根下的 `playbook.md`（用户自己的），新条目/修订只追加并引用旧版，不覆盖原规则

## 四、回头用闭环（别只沉淀不用）
- **开新仓前**：Mode A 立案时回查 playbook 对应条目与版本——适用条件、进场条件、仓位规则满足没？把规则锚点写进立案；未触发时不行动也能一致。
- **复盘时**：按 `_shared/trading-consistency.md` 对照当时版本，分开评估执行质量与策略有效性；不同环境或版本分别统计，不把临时例外自动炼成规律。
- **修订时**：追加 `[修正 date]` 记录，含旧→新版本、证据/来源、提出及确认时间、生效时间和适用范围；依据不足标待验证，不靠改版本号证明合理。保留旧版，不能重写旧交易的规则锚点。

## Worked example
虚构示例：有 5 笔卖 put 记录，全部留存，不按事后盈亏或“靠运气”删掉其中几笔。先查当时记录：若只有 3 笔明确属于同一规则版本且满足 IV 分位>75，另 2 笔条件不明，则分别记“本版本可比样本 3/10”和“条件待确认 2 笔”；不能从盈利或亏损倒推条件。收取权利金是现金流事实，未来波动率回落与策略优势仍是待验证假设。继续按同一规则收集盈利、亏损及未入场观察，达到流程门槛后再核对四关；不把这 5 笔的结果写成已证实的交易优势。
